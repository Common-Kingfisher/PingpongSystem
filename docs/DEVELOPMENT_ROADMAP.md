## 本轮确认的问题

### R01 / P0：后端比分合法性不足

位置：`backend/app/services/scores.py::_validate_scores/_validate_games`。

已运行隔离诊断：大比分校验接受 99:0；两局 12:5 也被识别为合法 2:0。前端约束无法代替服务端约束。改进：大比分必须与 games_to_win 一致；单局在未到平分延长阶段时应在目标分结束；延长阶段须恰好领先两分；异常结果走单独规则。

验收：默认规则接受 2:0、2:1；拒绝 1:0、3:0、99:0、平局和负分；单局接受 11:9、12:10，拒绝 12:5；录入与修改两个入口均验证。

### R02 / P0：改分没有覆盖所有下游

位置：`services/scores.py::revise_score`、`services/knockout.py::ensure_placement_matches/_create_direct_match/reset_branch`。

隔离 API 复现：两场半决赛结束生成季军赛后，反转一场半决赛结果返回 200，但季军赛参赛者不变。季军和败者排位来源是直接 Entry，没有 loser dependency。另复现：生成淘汰赛后仍可反转小组赛结果，返回 200，淘汰签表不随排名重建。

改进：先保存明确的来源关系；对所有受影响主签/季军/排位做统一保护。下游未开始可有确认后的重算，下游已经开始必须拒绝自动改写。小分补录如果不改变结果/出线也应被精确区分，不要一刀切误锁。

验收：季军等待、季军进行中、5–8 排位、7–8 排位、已生成淘汰的小组改分、无影响补录均有测试；不得悄悄替换已开打参赛者。

### R03 / P0：各组不同出线人数“能保存、不能继续”

位置：`domain/knockout.py::build_bracket`。隔离调用 `build_bracket([[1], [2, 3]], allow_extended=True)` 报“各组晋级人数不一致”。现有测试仅验证修改接口，随后解除/重分组恢复一致出线数，未验证异额出线闭环。

改进：实现不等额 GROUP_RANK 来源签位及轮空；或在实现前明确限制配置并给出提示，不能允许用户打完才报错。目标仍按用户要求实现逐组可调，不将临时限制写成需求取消。

验收：A 组前 1、B 组前 2；3 组各前 1；相同前 2 回归；出线超组人数、总出线少于 2、空组，均有明确处理。

### R04 / P0：同分规则与人工裁定未完整闭环

状态（2026-09-08）：部分同分拆分由 PR #6 完成；人工晋级裁定、审计历史和数据变化自动失效已实现。完整递归官方规则仍不在当前范围，系统在最后无法区分时交由主裁判裁定。

位置：`domain/ranking.py`、`services/rankings.py`、`RankingsPage.tsx`。

代码现状：胜场/净胜局/积分分桶，两人看直接交锋，多人看相关小分比率；若只有部分人的比率相同，整桶仍标并列；缺小分则提示补录。没有完整递归同分子集处理和人工裁定留痕。

不要悄悄把用户的“胜场优先”替换为另一套完整规则，也不要将目前的混合算法标为官方规则。人工裁定仅作用于晋级线，已记录依据、操作者、时间与排名快照。

验收：两人同分、三人循环互胜、部分人仍同分、缺小分、完整补录、出线线附近并列、弃权历史成绩和重算一致性。

### R05 / P1：秩序册会漏数据和误述规则

位置：`frontend/src/pages/OrderBookPage.tsx`。赛程使用 `slice(0, 40)`；三局两胜/11 分硬编码；缺完整主办/地点、规则文本、计划时间和签表。

改进：输出所有场次，动态读取规则；生成一致快照而非打印过程中混入不同时间数据；添加打印分页和重复表头。以后将组委会模板作为渲染层接入，不更换赛事数据模型。

### R06 / P1：数据库升级与交付可复现性

位置：`backend/app/db.py`、`backend/requirements.txt`、`start_demo.ps1`。

运行时 ALTER 迁移没有显式 schema 版本/备份流程；后端依赖只限定最低版本；启动脚本仅通过 node_modules 目录判断前端依赖完整。本轮实际遇到残留链接导致模块缺失，重装锁文件依赖后构建通过。

改进：版本化迁移、升级前备份、恢复演练；锁定验证环境；启动检查可执行模块，不自动删用户数据。并发写入原子性另加专项用例。

### R07 / P1：规模和功能边界未完整验收

完整低名次赛已覆盖 4 / 8 / 16 人无轮空标准签，并用递归独立排位区间保证败者不返回冠军主签；带轮空的非标准人数只输出由真实比赛确定的名次。120/15 仍缺全程证据；独立纯单淘汰和纯循环终局不完整；尚无休息时间、区域亲和、计划/实际时间、场次容量预估。需分阶段开发，UI 明示可用边界。

赛程调度的现状、数据模型、预览/确认流程和 S1–S3 实施顺序已整理在 `docs/SCHEDULING_V1_DESIGN.md`。在 S1 完成前，当前 `schedule-next` 只视为现场演示用的贪心填台，不宣称具备休息公平性或并发主裁判安全。

### R08 / P2：冠军之路和现场体验

当前自下而上轮次、比分、晋级者、冠军卡片高亮已存在，但连线由 CSS 行级装饰生成，不是按每场 prev_match 逐边绘制。建议改为按真实依赖定位 SVG 连线，并覆盖 4/8/16/32、长姓名、双打名称、轮空和打印。不让动画承担状态计算。

## 发布验收清单

- 16 人单打：导入 → 确认 → 小组 → 前二 → 八强 → 季军/5–8 → 唯一冠军。
- 双打：近积分配对、每人只入一个 Entry、未配齐阻止确认、调度无成员冲突、名次显示组合名。
- 出线：逐组不同人数、非 2 的幂签位、轮空均可继续到终局。
- 分数：正常/异常、补录/改分、同分以及所有下游保护均通过。
- 120 人/15 台：完整模拟到终局并打印全量内容，不以只创建成功代替验收。
- 并发：同球台同时安排、同场重复录分和请求重试不会产生双写/双赛。
- 工程：pytest、类型检查、构建、最小浏览器 E2E、契约漂移检查通过。
- 运维：全新目录 clone 后可启动；备份恢复验证；无真实个人名单/数据库/密钥入库。
- 发布只在上述相关项通过、无已知 P0 后打候选/正式标签。本次推送是交接基线，不是上线或验收标签。

## 留给组织者审查的决定

这些问题不阻塞本次文档和代码入库，但实施对应逻辑前需要确认：

- 同分末级：在已确认的胜场/净胜局/积分之后，是否采用当前两人直接交锋、多人相互成绩比较？需指定采用的赛事规程/规则版本，并明确递归比较和最后裁定办法。
- 弃权：整项退出与单场弃权是否不同？之前已完成成绩是否保留？不要将一次弃权自动推断为退出全赛。
- 现场规模与时间：120/15 是近期实际使用规模还是上限？最低休息分钟数、同组固定台/区域策略尚未确定。
- 低名次扩展：超出 8 人无轮空主签后，要逐名排到底还是允许名次区间？当前按已接受的小范围实现保留，不冒充全规模完成。
- 排期与分工：队友可投入工时、发布日期和独立复核人尚未明确；确认后再把里程碑换算为日程。

无需重新讨论已确认的事项：不做双败；默认三局两胜 11 分；常规大比分；季军创建时选择；正式目录唯一；先浏览器打印再适配官方模板。
