## 本轮确认的问题

### R01 / P0：后端比分合法性不足

位置：`backend/app/services/scores.py::_validate_scores/_validate_games`。

已运行隔离诊断：大比分校验接受 99:0；两局 12:5 也被识别为合法 2:0。前端约束无法代替服务端约束。改进：大比分必须与 games_to_win 一致；单局在未到平分延长阶段时应在目标分结束；延长阶段须恰好领先两分；异常结果走单独规则。

验收：默认规则接受 2:0、2:1；拒绝 1:0、3:0、99:0、平局和负分；单局接受 11:9、12:10，拒绝 12:5；录入与修改两个入口均验证。

### R02 / P0：改分没有覆盖所有下游

位置：`services/scores.py::revise_score`、`services/knockout.py::ensure_placement_matches/_create_direct_match/reset_branch`。

隔离 API 复现：两场半决赛结束生成季军赛后，反转一场半决赛结果返回 200，但季军赛参赛者不变。季军和败者排位来源是直接 Entry，没有 loser dependency。另复现：生成淘汰赛后仍可反转小组赛结果，返回 200，淘汰签表不随排名重建。

改进：先保存明确的来源关系；对所有受影响主签/季军/排位做统一保护。下游未开始可有确认后的重算，下游已经开始必须拒绝自动改写。小分补录如果不改变结果/出线也应被精确区分，不要一刀切误锁。

验收：季军等待、季军进行中、5–8 排位、7–8 排位、已生成淘汰的小组改分、无影响补录均有测试；不得悄悄替换已开打参赛者。

### R03 / P0：各组不同出线人数“能保存、不能继续”

位置：`domain/knockout.py::build_bracket`。隔离调用 `build_bracket([[1], [2, 3]], allow_extended=True)` 报“各组晋级人数不一致”。现有测试仅验证修改接口，随后解除/重分组恢复一致出线数，未验证异额出线闭环。

改进：实现不等额 GROUP_RANK 来源签位及轮空；或在实现前明确限制配置并给出提示，不能允许用户打完才报错。目标仍按用户要求实现逐组可调，不将临时限制写成需求取消。

验收：A 组前 1、B 组前 2；3 组各前 1；相同前 2 回归；出线超组人数、总出线少于 2、空组，均有明确处理。

### R04 / P0：同分规则与人工裁定未完整闭环

状态（2026-09-08）：部分同分拆分由 PR #6 完成；人工晋级裁定、审计历史和数据变化自动失效已实现。完整递归官方规则仍不在当前范围，系统在最后无法区分时交由主裁判裁定。

位置：`domain/ranking.py`、`services/rankings.py`、`RankingsPage.tsx`。

代码现状：胜场/净胜局/积分分桶，两人看直接交锋，多人看相关小分比率；若只有部分人的比率相同，整桶仍标并列；缺小分则提示补录。没有完整递归同分子集处理和人工裁定留痕。

不要悄悄把用户的“胜场优先”替换为另一套完整规则，也不要将目前的混合算法标为官方规则。人工裁定仅作用于晋级线，已记录依据、操作者、时间与排名快照。

验收：两人同分、三人循环互胜、部分人仍同分、缺小分、完整补录、出线线附近并列、弃权历史成绩和重算一致性。

### R05 / P1：秩序册会漏数据和误述规则

### A1.1 / P1：关键赛事操作审计（真实赛事试点前必须补齐）

位置：`backend/app/services/knockout.py`（撤销淘汰签表）、`backend/app/routers/tournaments.py`（删除赛事）。

现状：A1 新增的"撤销淘汰签表"只返回删除计数，删除赛事只做名称确认，两者都没有记录操作者、理由与时间；人工晋级裁定已有 operator / reason / 时间留痕，两类操作的审计标准不一致。**A2 已评估并决定暂不实现**：单独给撤销加审计会与"删除赛事永久审计"割裂（赛事物理删除会级联带走审计行），需要与归档/软删除一起设计，否则只是表面审计。

落地设计（供 A3 或独立批次实现，不在 A2 内实现）：
  1. 新表 `tournament_operation_audits`：`id`、`tournament_id`（FK，CASCADE 仅供撤销类操作）、`operation`（`KNOCKOUT_UNDO` / `TOURNAMENT_DELETE` / `SCORE_FORCE_EDIT`）、`operator_name`、`reason`、`impact_json`（影响范围快照，例如删除的主签/排位场次数）、`created_at`。
  2. 删除赛事若要"永久审计"，审计行必须与赛事解耦（例如保留 `tournament_name` 快照且不挂 CASCADE，或先把赛事归档为只读快照），因此与 archive / soft-delete 架构一起做。
  3. 接口：撤销签表的 body 增加可选 `operator_name` / `reason`（缺省仍可撤销，仅记录为空）；导出 `TournamentExport.operation_audits` 追加即可（兼容追加，`schema_version` 不变）。

要求：真实赛事试点前完成第 1、3 项；删除赛事永久审计与归档架构绑定。
