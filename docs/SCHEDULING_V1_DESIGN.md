# 主裁判赛程调度 V1 方案

更新日期：2026-09-08。本文是下一阶段实现合同，不代表当前代码已经具备这些能力。

## 目标与边界

V1 面向单机现场的主裁判，解决“下一批谁上哪张台、为什么、是否安全”三个问题。它不是多人协作系统，也不生成官方分钟级秩序册；演示自动播放继续与正式调度隔离。

当前 `schedule-next` 按比赛记录顺序贪心填满空闲球台，已经阻止同一运动员同时上两场、同一球台同时放两场，但尚未记录休息时间、推荐理由、主裁判覆盖原因和计划/实际时间。选手赛程页也是只读查询，不是调度工作台。

## 主裁判操作流程

1. 系统生成“下一批建议”，此时不修改比赛和球台。
2. 每条建议显示对阵、阶段、建议球台、等待情况、最近一场结束时间和推荐原因。
3. 主裁判可以移除、换台或加入其他当前可上场的比赛。
4. 点击“确认上台”后，整批在一个事务中生效；任一比赛或球台状态已变化，则整批拒绝并刷新建议。
5. 需要突破休息时间等软限制时，必须填写裁定理由和操作者；硬冲突不能覆盖。

正式比赛默认使用“预览 → 确认”。Demo 才允许连续自动推进，并显示醒目的演示标识。

## 约束与排序

### 不可绕过的硬约束

- 比赛状态为 `WAITING`，双方 Entry 已确定，所有上游比赛已结束。
- 球台属于当前赛事且为 `FREE`。
- 任一运动员当前不在其他 `PLAYING` 比赛；双打按全部成员检查。
- 同一批次内运动员和球台均不得重复。
- 小组/淘汰阶段及签位依赖保持现有业务边界。

### 可配置的软约束

- 最短休息时间：以该 Entry 所有成员中最晚的上一场结束时间计算。具体分钟数由赛事创建或现场设置决定，不在代码中写死。
- 球台亲和：同组集中在相邻或指定球台，减少寻找场地；没有配置时不启用。
- 阶段优先：默认先完成当前阶段，不把低名次排位长期饿死。

### 推荐分排序

先过滤硬约束，再按稳定的元组排序，避免“黑盒分数”难以解释：

1. 主裁判手动置顶；
2. 已满足最短休息时间且等待最久；
3. 能解锁更多下游比赛；
4. 让各小组完成进度更均衡；
5. 符合球台亲和；
6. 比赛 ID 作为最终稳定顺序。

接口必须返回 `reason_codes` 和人类可读说明，例如“已休息 18 分钟、等待最久、完成后解锁半决赛”。前端只展示解释，不自行重算优先级。

## 建议数据结构

### 比赛时间事实

在 `matches` 增加：

- `called_at`：确认上台时间；
- `started_at`：实际开赛，可在首个录分动作或主裁判确认时写入；
- `finished_at`：结果最终确认时间；
- `schedule_version`：调度并发版本号。

历史库迁移后这些字段允许为空。休息时间只使用 `finished_at`，缺失时显示“历史时间未知”，不得假设已经休息充分。

### 调度策略

`schedule_policies`：`tournament_id`、`min_rest_minutes`、阶段权重、球台区域配置、`updated_by`、`updated_at`。第一版 UI 只开放最短休息时间，其他字段先保持服务端默认策略。

### 调度审计

`schedule_batches`：批次 ID、赛事、模式 `AUTO/MANUAL`、操作者、生成时间、确认时间、基线版本、状态。

`schedule_assignments`：批次、比赛、球台、排序位置、`reason_codes`、推荐快照、是否人工覆盖、覆盖理由。释放球台不删除历史，而是记录失效状态和时间。

## API 草案

- `POST /api/tournaments/{id}/schedule-preview`：传可选空闲球台和置顶比赛，返回建议、不可用候选及原因；不写业务状态。
- `POST /api/tournaments/{id}/schedule-confirm`：传预览批次 ID、操作者和覆盖理由；原子确认整批。
- `GET /api/tournaments/{id}/schedule-candidates`：返回可上场、休息中、等待签位三类列表。
- `GET /api/tournaments/{id}/schedule-history`：供主裁判追查谁在何时安排或释放比赛。

现有 `POST /schedule-next` 在迁移期保留给 Demo；正式赛事前端不再直接调用。手动 `assign-table` 同样补充操作者、理由与版本检查。

## 页面方案

比赛控制台新增一块紧凑的“下一批建议”：

- 顶部显示空闲球台、可上场数、休息中人数和最长等待时间。
- 建议以横向卡片排列；卡片直接显示推荐原因和风险，不藏在二级弹窗。
- “生成建议”与“确认上台”使用不同按钮；确认前摘要写明将安排几场、占用哪些球台。
- 候选抽屉分为“可上场 / 休息中 / 等待上游”，主裁判能看见为什么没被推荐。
- 手动突破软限制时使用确认对话框，并记录理由、操作者和时间。

选手赛程页继续只读，但用“预计顺序”代替虚假的精确开赛时间；只有接入正式时间计划后才显示计划时刻。

## 分阶段落地

### S1：事实和安全

增加时间戳、调度版本和审计表；把批量安排变成原子事务；补同一请求重试、过期预览、双打成员冲突测试。完成后才可称为“正式调度安全”。

### S2：可解释推荐

实现候选分类、最短休息配置、稳定排序和推荐理由；控制台使用预览/确认流程。用固定数据验证同一输入得到同一建议。

### S3：计划与容量

增加预计比赛时长、场次数量/球台容量分析、计划时间和延误滚动。等组委会模板确定后，再把同一数据接入正式秩序册；不要先写死模板。

## 验收清单

- 单打与双打都不会出现同一自然人同时上场。
- 两位主裁判窗口基于同一预览确认时，只允许一个成功，另一个收到清楚的过期提示。
- 未达到最短休息时间的比赛不会自动推荐；人工覆盖留下理由、操作者和时间。
- 一批中的任一球台或比赛状态变化时，不产生半批成功。
- 释放、换台、重新安排均可追溯，历史不被覆盖。
- 16 人/4 台固定数据的推荐顺序稳定；120 人/15 台完成性能测试。
- 正式模式没有 Demo 连续推进入口，Demo 数据不会进入正式赛事。

## 开工前只需确认的产品参数

- 默认最短休息分钟数，以及季军/决赛是否使用不同值。
- 是否需要固定小组球台区域；如果需要，现场球台如何分区。
- 主裁判人工覆盖软限制时，是否只填理由，还是还需二次确认人。

这些参数不影响 S1 的数据和并发安全工作，可在进入 S2 前确定。
