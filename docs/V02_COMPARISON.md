## 对比依据与优先级

已读取工作区 `v0.2/` 中两份 Markdown：

- `Field Demo v0.2.md`：48 节工程方案。

同时提取了对应两个 DOCX 的正文作交叉核对；两个 DOCX 都没有内嵌图片。原文件位于仓库外，本轮不覆盖或冒充已经修订。原稿标题明确写着 DRAFT/讨论稿，不能仅凭文件夹叫 V0.2 就视为所有条款已经定稿。

执行优先级：用户后续明确确认的范围 > 与其不冲突的 V0.2 需求 > 早期 Demo 说明。工程原稿中的模型、供应商价格和三天预算属于历史建议，本轮没有进行供应商事实核验，不将其写成当前采购建议。

状态定义：“已实现”表示找到对应实现，仍受验证范围限制；“部分”表示只有有限范围；“未实现”表示本轮在相关源码/结构未找到；“已调整”表示用户明确改变原要求，不应算漏做。

## 工程方案差异

| 工程要求 | 现状 | 后续动作 |
|---|---|---|
| 保留原栈，不引入重型状态库 | 符合；API 仍集中在 api.ts | 保留 |
| Service/domain 边界清晰 | 已分层，但部分编排/校验仍在 router，存在旧函数与新路径并存 | 按缺陷涉及范围渐进整理 |
| OpenAPI 自动生成 TS 类型 | 有导出脚本、快照且与应用一致；没有 openapi-typescript/生成类型 | 先补契约生成和漂移检查 |
| 显式迁移、升级脚本、备份 | db.init_db 运行时检查列并 ALTER，正是原稿禁止的方案 | 增加版本化迁移、备份/恢复演练 |
| 事务、SQLite 并发 | 每请求连接、foreign_keys、check_same_thread=False 保留 | 并发排台/录分仍须专项验证，不能只靠串行查询 |

| 浏览器 E2E 与120/15全流程 | 有后端 API 流程测试；未找到持久化的 Playwright 套件/CI | 建最小浏览器流程并增加规模验收 |

## 哪些不能混淆

- “双败”与“低名次排位”是两种不同规则。当前排位不能回主签夺冠。
- 小组积分不等于运动员 rating；前端不能自行用 rating 决定三四名。
- “表中有 120 上限”不等于 120/15 全流程通过；“有字段”不等于业务闭环。
- 当前排名是项目自定义规则加部分比率逻辑，不是已经校验通过的完整 ITTF 官方规则。
- 双打已实现主体，是相较原稿提前做了；场馆、时段、通用 Stage、迁移等则尚未达到原稿目标。

## 对原计划的建议结论

保留“正确性优先、保留栈、契约先行、清晰 ownership”的原则。删除双败相关工期与验收项；将双打、季军、有限排位和可选小分写入新基线；不再承诺三天一次补完所有通用架构。先用可回归的核心赛事流程建立发布候选，再逐步扩展场地、时间和模板。
